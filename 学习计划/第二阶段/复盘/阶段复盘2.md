### 2. 存在问题

1. **H265 性能瓶颈**：第一版在主线程内串行解码/编码，多路/高帧率下帧率严重降低（自测记录1 问题1），属功能层面缺陷。
2. **工程规范缺失**：`build_2004/` 下 CMake 缓存、`.o`、编译产物等生成文件混入 git 提交，缺少 `.gitignore` 管理。
3. **自测覆盖不全**：实测以 JPEG 数据包为主，H265 链路帧率复测。
4. **复用代码理解不深**：`H26XDecoder` 为从 plugin1清洗复制而来，对其 FFmpeg 内部实现消化不足，初期排障依赖较少。

### 3. 经验总结

1. **先跑通最小闭环，再叠加优化**：第一版保证功能可运行（编译通过 + 直通 + 单路 H265），第二版才上线程池并行，问题定位和回退都清晰。
2. **性能问题要靠真实数据实测暴露**：JPEG 直通测不出 H265 瓶颈，只有用 H265 数据包 + 高帧率场景跑，才能发现串行导致的降帧。
3. **线程池并行设计要点**：按数据单元（每路相机）划分任务、每路独立 `CameraSlot`（decoder+encoder+mutex）避免锁竞争、`waitAll` 带超时兜底防阻塞、先等全部任务完成再返回保证栈引用安全。
4. **全程留痕可追溯**：任务定义 → 拆解 → 提交 → 自测 → 流程检查逐环节留痕，问题、提交号、拆解项互相可追溯。
5. **多平台尽早验证**：Ubuntu 18.04/20.04 存在 FFmpeg 版本差异（<4.0 需 `avcodec_register_all`），双平台编译脚本预留。

### 4. 不足与改进

1. 性能风险未在任务定义阶段预判，依赖自测兜底发现 —— 改进：任务确认时就把性能边界（多路/帧率）列为完成标准的一部分。
2. 工程规范（构建产物管理、`.gitignore`）在开发后期才意识到 —— 改进：开发前置工程基线，构建产物不入库。

### 5. 对第三阶段建议

1. 进入真实问题闭环前，先完整读懂待改模块的代码，避免复制-照搬式开发。
2. 问题分析要带证据链（日志、复现步骤、代码定位），根因判断可自证。
3. 边界与性能风险在任务定义阶段就评估，不等到自测才暴露。
4. 先补齐第二阶段欠账：H265 帧率复测、x86_1804 平台验证。
