# 军事博弈：逻辑、工程实现与演示汇报梳理

分析日期：2026-11-15。

依据：用户提供的 `/media/sf_share_file/J事博弈.pdf`（5 页）及当前工程源码。本文为静态代码与文档核对，不代表已完成现场联调，不修改业务代码。以下页码为 PDF 物理页码；代码路径相对于工程根目录。

## 一、先给结论：应该如何定位这个项目

建议定位为：**面向虚拟红蓝对抗场景的态势回放、规则交互和指标对比演示原型。**

目前不能直接定位为“已经具备最优策略求解能力的军事博弈 AI 系统”。原因是：

1. PDF 同时包含概念说明、Python 求解示例、接口设想与加权评价升级方向，它们不是已经完成的同一条工程链路。
2. 工程有两套不同的演示路径：旧版“规则选择＋CSV 态势回放”；新版“场景输入＋播放控制＋指标评分”。
3. 新版的核心计算是归一化加权评分，不是纳什均衡，也没有在已检查的本工程代码中找到博弈树求解实现。
4. 大模型文字展示接口存在，但未据此发现从博弈态势输入到模型推理再到推荐方案的完整专用闭环。
5. 旧版裁决调用被注释，新版配置和字段存在一致性问题，演示前必须预检。

最稳妥的汇报主线是：**文档提出什么 → 工程当前实现什么 → 一次场景如何运行 → 结果能说明什么 → 尚有哪些边界。**

## 二、PDF 中的军事博弈逻辑

### 2.1 文档的逻辑结构

| PDF 位置 | 内容 | 应如何理解 |
|---|---|---|
| 第 1 页 | 对抗、情报、人机能力差异，激烈对抗/克制行动矩阵 | 业务背景与交互规则的概念层 |
| 第 2 页 | 红蓝状态、资源、地形、天气；`nashpy` 示例 | 建模与求解的示意，不是当前 C++ 实现证据 |
| 第 3 页 | 规则、物理仿真、AI 决策、数据层 | 目标架构；AI 作为辅助解释和方案建议来源 |
| 第 4 页 | 想定运行、态势与规则 topic、推荐结果显示 | 计划中的系统交互流程 |
| 第 5 页 | 维度系数与加权平均评价 | 工程新版指标评分的对应方向；PDF 中公式未完整呈现 |

抽象业务流程可以概括为：

```text
虚拟场景与双方状态
    ↓
规则、约束与评价标准
    ↓
双方行为交互与场景播放
    ↓
结果评价
    ↓
结果解释、人工确认与复盘
```

这里要区分三个层次：**场景会动**证明播放链路；**能输出分数**证明评价计算；**能够求最优策略**还需要独立的策略建模与求解证据。前两者不能自动推出第三者。

### 2.2 PDF 中需要修正的理论表述

- “双方受损”或“局势稳定”的文字矩阵，不足以证明零和。零和必须落实到具体收益定义，而当前工程评分未建立双方得分相加为零的约束。
- 第 2 页 `support_enumeration()` 示例是收益矩阵上的均衡枚举，并非博弈树搜索；示例中的红蓝收益也并非每个格子都互为相反数。
- PDF 里的“让大模型自己胡言乱语”不能转化成正式产品能力描述。汇报时应改为“基于结构化输入给出辅助说明，结论可追溯、由人工审核”。
- PDF 第 5 页缺失可读公式，因此下文公式依据 C++ 实现还原，不宣称是 PDF 原公式。

### 3.2 路径 A：旧版规则窗口＋CSV 回放

```text
主窗口“军事博弈”
    → GkdDataFusion_by 窗口
    → 选择红方/蓝方“激烈对抗”或“克制行动”
    → 点击开始时同步规则到 C2Manager
    → 两个线程播放目标、平台轨迹
    → QB/301：目标态势；QB/303：己方平台态势
    → C2Manager 接收、更新场景
```

关键实现：

- 入口：`mainwindow.cpp:196`。
- 四个选项分为红、蓝两个互斥组：`Src/gkd_game_test/GkdDataFusion_by.cpp:77`。
- 点击开始时读取策略，调用 `setBYType` 并开启两个线程：`Src/gkd_game_test/GkdDataFusion_by.cpp:155`。运行中切换单选按钮没有在这里形成独立的实时规则更新链路。
- 数据来源是程序目录下 `data/DataFusion/fusiondata_new.csv`：`Src/gkd_game_test/GkdDataFusion_by.cpp:251`。
- 目标按原始轨迹推送；己方由同一份数据反转列表和路径后推送：`Src/gkd_game_test/GkdDataFusion_by.cpp:361`、`Src/gkd_game_test/GkdDataFusion_by.cpp:401`。
- 界面频率控制的是线程逐条发送间隔，不宜直接宣称“每个目标都达到界面设置频率”。

**关键边界：四策略裁决当前不能认定可运行。**

`Src/gkd/c2manager.cpp:2030` 创建了两个空列表，但填充它们的 `GetConnTargetAndPlatform(...)` 被注释；后续四种策略分支遍历这些空列表。因此，虽然有移除对象、特效等分支代码，不能汇报为“已验证四种策略产生不同损耗结果”。

另外：

- 名为 `CalBoYi()` 的函数存在，但其线程启动同样被注释：`Src/gkd_game_test/GkdDataFusion_by.cpp:171`。
- “复位”仅调用停止函数，不是完整重建场景和清零索引：`Src/gkd_game_test/GkdDataFusion_by.cpp:150`。
- 界面“判定”按钮未在该类中找到对应业务绑定，不能仅凭按钮存在宣称支持手工裁决。
- 四策略分支中的 `sn % 2` 是按消息计数奇偶分支，不是经过统计定义的 50% 损失概率。
- `rand()` 出现在模拟融合统计日志中，不代表已实现随机对手策略或随机轨迹生成。

### 3.3 路径 B：新版场景输入＋回放＋指标评价

这是更适合解释现有架构的主线，但仍需部署预检和现场验证。

```text
外部场景系统
    │ RPC: addEnemyEquip（双方对象、路径、指标）
    ▼
C2Manager
    ├─ 清理上一轮评价状态
    ├─ 按 force 缓存双方输入指标
    └─ MQTT: /control/1，封装 target_list
                    ▼
                  XjSim
                    │ RPC playControl 经 C2Manager 转 /control/2
                    └─ 按路径逐点发布 QB/301
                                      ▼
                               C2Manager 更新目标位置

外部场景系统
    │ RPC: pushRedTgtPos（当前位置）
    ▼
C2Manager
    └─ 与最近缓存目标位置比较
       → 达到源码内置接近阈值，且本轮未结束
       → jsbyWeightedAverage()
       → 外部可视化“博弈结论”文本窗口
```

源码锚点：

1. `addEnemyEquip` 回调及双方指标输入：`Src/gkd/c2manager.cpp:767`。
2. `/control/1` 发布：`Src/gkd/c2manager.cpp:783`。
3. `playControl` → `/control/2`：`Src/gkd/c2manager.cpp:880`。
4. `XjSim` 接收两类控制：`Src/xjsim/xjsim.cpp:1517`。
5. 轨迹播放及 `QB/301` 发布：`Src/xjsim/xjsim.cpp:1735`。
6. 目标位置缓存：`Src/gkd/c2manager.cpp:1903`。
7. `pushRedTgtPos` 接近判定和一次性评价：`Src/gkd/c2manager.cpp:904`。
8. 指标评分与结果窗口：`Src/gkd/c2manager.cpp:3654`。

需要特别解释：

- `force` 在指标输入中转换为布尔值，非零进入目标侧、零进入己方侧；它不能与其他消息中的 `forcetype` 混用。
- 评价使用场景输入时缓存的指标值，不是不断根据运动消耗更新指标的物理仿真。
- 接近判定使用最近一条缓存目标位置，不是按目标 ID 遍历匹配全部红蓝组合。
- 每轮 `_jsby_isEnd` 只允许首次触发；重新提交场景会调用 `reSetJSBY()`。
- 路径播放没有按 `force` 筛选对象，输入对象列表与目标回放列表的边界需要现场确认。
- 源码接收 `rate/currenttime`，但 `jsbyPlay()` 没有使用它们做倍速或断点续播；不应演示为已支持。

### 3.4 指标评价到底怎么算

配置格式由解析器确定：

```text
指标名称 = 复合参数标志_最小值_权重_最大值
```

依据：`Src/gkd/c2manager.cpp:3609`。

实现依次执行：

```text
单指标归一化值 = clamp((当前值 - 最小值) / (最大值 - 最小值), 0, 1)
单指标贡献值   = 单指标归一化值 × 权重
某一方综合分数 = 该方所有对象所有指标贡献之和 / 该方所有对象所有指标权重之和
```

依据：`Src/gkd/c2manager.cpp:3706`、`Src/gkd/c2manager.cpp:3759`。

这实际是按权重汇总的指标平均值。代码没有先按装备形成独立分数、再按装备重要性进行第二层加权的显式流程，因此不宜直接称为已经实现完整的“两次加权平均”。

**界面“胜出概率”的文字需要谨慎解读。**

例如两个独立分数为 0.7 和 0.6，代码会显示 70% 和 60%，并不要求总和为 100%。这只能解释为“配置条件下的综合评价得分”，不能当作统计胜率，更不能视作真实结果预测。依据：`Src/gkd/c2manager.cpp:3816`。

其他边界：缺失指标被填为 `-99`；未实现明确的成本型/收益型指标方向区分；计算未见针对零权重总和及最大最小值相等的有效防护；`is_complex` 被解析但未见用于复合指标计算。

### 3.5 AI 在哪里，哪里还不能算 AI

- PDF 第 4 页提出 `zk/ts`、`zk/gz`；本工程检索未见对应发布/订阅实现。
- 工程使用的是 `QB/301`、`QB/303`、`/control/1`、`/control/2` 等实际链路，不能将文档 topic 当作现行协议。
- `SHOW_CHAT` 分支接收外部文本，并调用可视化 SDK 展示：`Src/xjsim/xjsim.cpp:450`、`Src/xjsim/xjsim.cpp:1792`。
- 这证明“可显示外部回答”，不证明“该回答由本工程完成模型推理”，也不证明已形成专用博弈推荐闭环。
- AI 如需演示，建议只展示虚拟场景的状态摘要、评分解释和缺失信息提示，不把生成文字包装成最优策略或确定性结论。

## 五、如何演示：建议采用“核心链路＋可选 AI 展示”

### 5.1 演示目标

演示“输入可追踪、过程可观察、评分可解释、边界说得清”。不要以一次动画或一段生成文字证明真实效果。

建议展示三个区域：左侧场景态势，中间场景参数/指标，右侧评分结论与消息日志。只有单屏时按此顺序切换。

### 5.2 开场前检查清单

1. 备份程序目录 `config.ini`、`gkd_config.ini`，确认不存在启动覆盖风险。
2. 启动并确认 MQTT Broker 和外部可视化 RPC 服务就绪，再启动应用。
3. 核对 `config.ini` 中 MQTT/RPC 地址和端口；不要把 `gkd_config.ini` 中同名网络段当然认作主连接来源。
4. 确认 `addEnemyEquip`、`playControl`、`pushRedTgtPos` 回调能到达。外部系统具体按钮名称不在本仓库可核实范围内。
5. 用一对虚拟对象准备固定场景，每条路径至少两个有效点，字段类型与名称逐项核对。
6. 检查指标模板非空、最大值大于最小值、权重总和为正；先人工核算一轮期望分数。
7. 完整彩排一次“加载—播放—触发—结果—重载”，保存过程录像、消息样本与结果截图。
8. 如展示 AI，额外确认外部服务链路；若只发送预制文字，现场明确说明这是展示接口联调。

| 时间 | 画面与操作 | 建议讲解 | 验收证据 |
|---|---|---|---|

### 5.4 备用方案

- RPC 或渲染异常：切换预录视频，明确标注“预录”，用消息日志解释链路。
- 未触发结论：检查目标位置是否已由 `QB/301` 更新、位置回调是否到达、上一轮是否已结束；不要现场修改触发阈值凑效果。
- 分数异常：展示输入与配置审计，不把 `NaN`、缺失字段或异常百分数解释成有效结果。
- AI 服务不可用：省略该段；预制文本只能称为展示接口样例。
